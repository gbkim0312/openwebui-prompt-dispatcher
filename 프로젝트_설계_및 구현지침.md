# Open WebUI Prompt Dispatcher 구현 지침

## Hexagonal Architecture 적용 버전

Python 기반의 `prompt-dispatcher` Docker 서비스를 구현한다.

이 서비스는 `*.job.yaml` 파일에 지정된 Cron 일정에 따라 Open WebUI API를 호출하고, 생성된 응답을 하나 이상의 메시지 채널로 전달한다.

다음 요구사항을 설계의 최우선 기준으로 삼는다.

* Hexagonal Architecture
* 높은 테스트 가능성
* 외부 시스템과 비즈니스 로직의 분리
* 채널 Adapter의 지속적인 추가
* Fake Adapter를 통한 외부 통신 없는 테스트
* Framework와 인프라에 독립적인 Application Core
* Dockerfile을 이용한 로컬 이미지 빌드
* Compose에서는 빌드 없이 로컬 이미지 태그 사용

초기 실제 채널 Adapter는 다음 두 가지를 구현한다.

1. Telegram
2. Nextcloud Talk

테스트와 로컬 검증을 위한 다음 Adapter도 반드시 구현한다.

3. Fake Channel
4. Fake Open WebUI Client
5. In-memory Execution Repository

# 1. 전체 실행 흐름

```text
*.job.yaml 로드
        ↓
Job 정의 검증
        ↓
Cron 스케줄 등록
        ↓
예약 시각 도달
        ↓
RunJob Use Case 호출
        ↓
프롬프트 로드 및 렌더링
        ↓
OpenWebUiPort 호출
        ↓
모델 응답 검증
        ↓
MessageChannelPort 구현체들로 전송
        ↓
ExecutionRepositoryPort에 실행 결과 저장
```

Application Core는 다음 사항을 알면 안 된다.

* Requests 또는 HTTPX
* Telegram Bot API URL
* Nextcloud OCS API URL
* SQLite
* SQLAlchemy
* APScheduler
* FastAPI
* 환경변수
* YAML
* Docker
* 파일 시스템의 구체적인 경로

Application Core는 Port 인터페이스와 Domain Model만 사용해야 한다.

# 2. Hexagonal Architecture 원칙

프로젝트는 다음 세 영역으로 분리한다.

```text
Domain
Application
Adapters / Infrastructure
```

## 2.1 Domain

Domain에는 순수한 비즈니스 모델과 규칙만 둔다.

예:

* Job
* Schedule
* PromptDefinition
* ChannelDestination
* ExecutionPolicy
* Execution
* DeliveryResult
* ExecutionStatus
* DeliveryStatus

Domain 객체는 다음에 의존하면 안 된다.

* Pydantic BaseSettings
* FastAPI
* APScheduler
* Requests
* HTTPX
* SQLite
* SQLAlchemy
* YAML Parser

Pydantic을 사용하더라도 외부 입력 DTO와 Domain Model을 명확하게 분리한다.

Domain은 가능한 한 Python 표준 라이브러리만 사용한다.

## 2.2 Application

Application은 Use Case와 Port를 포함한다.

주요 Use Case:

* LoadJobs
* ValidateJobs
* RegisterSchedules
* RunJob
* DeliverMessage
* ListJobs
* RecoverAbandonedExecutions

Application은 외부 시스템을 직접 호출하지 않고 Port를 호출한다.

## 2.3 Adapters

외부 시스템별 구현은 Adapter로 둔다.

Inbound Adapter:

* APScheduler Adapter
* CLI Adapter
* FastAPI Adapter
* YAML Job Loader Adapter

Outbound Adapter:

* Open WebUI HTTP Adapter
* Telegram Channel Adapter
* Nextcloud Talk Channel Adapter
* Fake Channel Adapter
* SQLite Execution Repository Adapter
* In-memory Execution Repository Adapter
* File Prompt Loader Adapter
* Fake Prompt Loader Adapter
* System Clock Adapter
* Fake Clock Adapter

# 3. 의존성 방향

의존성 방향은 항상 외부에서 내부를 향해야 한다.

```text
Adapters
   ↓
Application
   ↓
Domain
```

금지되는 의존성:

```text
Domain → Application
Domain → Adapters
Application → Concrete Adapter
```

허용되는 의존성:

```text
Adapter → Application Port
Application → Domain
Application Service → Port Interface
```

Application 계층에서 다음과 같은 코드는 금지한다.

```python
requests.post(...)
sqlite3.connect(...)
os.getenv(...)
yaml.safe_load(...)
```

Application은 생성자 주입으로 전달받은 Port만 사용한다.

# 5. 핵심 Domain Model

## 5.1 Job

Job은 다음 정보를 가진다.

```text
id
name
enabled
schedule
openwebui_options
prompt_definition
destinations
execution_policy
```

Job은 외부 YAML 구조와 직접 결합하지 않는다.

YAML Adapter가 외부 DTO를 Domain Job으로 변환한다.

## 5.2 ChannelDestination

채널 목적지는 다음과 같이 일반화한다.

```python
@dataclass(frozen=True)
class ChannelDestination:
    channel_type: str
    target: str
    options: Mapping[str, object]
```

Application은 `telegram`, `nextcloud_talk`의 내부 동작을 알지 않는다.

`channel_type`에 대응하는 `MessageChannelPort` 구현체를 Resolver에서 조회한다.

## 5.3 ExecutionStatus

최소 다음 상태를 지원한다.

```text
RUNNING
SUCCESS
PARTIAL_SUCCESS
FAILED
SKIPPED
ABANDONED
```

## 5.4 DeliveryStatus

최소 다음 상태를 지원한다.

```text
PENDING
SUCCESS
FAILED
SKIPPED
```

# 6. Application Port 정의

Port는 `typing.Protocol` 또는 ABC로 정의한다.

일관성을 위해 한 가지 방식으로 통일한다. 구조적 타이핑과 Fake 구현 편의를 고려하여 `Protocol` 사용을 권장한다.

## 6.1 OpenWebUiPort

```python
from typing import Protocol

from prompt_dispatcher.domain.job import OpenWebUiRequest
from prompt_dispatcher.domain.job import OpenWebUiResponse


class OpenWebUiPort(Protocol):
    def generate(
        self,
        request: OpenWebUiRequest,
    ) -> OpenWebUiResponse:
        ...
```

Application은 HTTP 응답 JSON 구조를 알면 안 된다.

HTTP Adapter가 다음 형태로 변환해서 반환한다.

```python
@dataclass(frozen=True)
class OpenWebUiResponse:
    content: str
    model: str | None = None
    tool_calls: tuple[str, ...] = ()
```

## 6.2 MessageChannelPort

```python
from typing import Protocol

from prompt_dispatcher.domain.delivery import OutboundMessage
from prompt_dispatcher.domain.delivery import DeliveryReceipt


class MessageChannelPort(Protocol):
    @property
    def channel_type(self) -> str:
        ...

    def send(
        self,
        target: str,
        message: OutboundMessage,
    ) -> DeliveryReceipt:
        ...
```

채널 구현체는 자신에게 필요한 환경변수와 외부 API 처리만 담당한다.

Application은 메시지 분할이나 API URL을 알지 않는다.

채널별 메시지 길이 제한과 포맷 변환은 해당 Adapter 책임으로 한다.

## 6.3 ExecutionRepositoryPort

```python
class ExecutionRepositoryPort(Protocol):
    def try_start(
        self,
        execution: Execution,
    ) -> bool:
        ...

    def complete(
        self,
        execution_id: str,
        result: ExecutionResult,
    ) -> None:
        ...

    def add_delivery(
        self,
        execution_id: str,
        result: DeliveryResult,
    ) -> None:
        ...

    def find_running(
        self,
        job_id: str,
    ) -> Execution | None:
        ...

    def recover_abandoned(
        self,
        older_than: datetime,
    ) -> int:
        ...
```

`try_start()`는 중복 실행 방지를 위해 원자적으로 동작해야 한다.

## 6.4 JobRepositoryPort

```python
class JobRepositoryPort(Protocol):
    def find_all(self) -> Sequence[Job]:
        ...

    def find_by_id(
        self,
        job_id: str,
    ) -> Job | None:
        ...
```

초기 구현은 YAML Job Repository Adapter다.

향후 다음 Adapter로 교체 가능해야 한다.

* DatabaseJobRepository
* NextcloudJobRepository
* HTTPJobRepository
* InMemoryJobRepository

## 6.5 PromptLoaderPort

```python
class PromptLoaderPort(Protocol):
    def load(
        self,
        prompt_reference: PromptReference,
    ) -> str:
        ...
```

## 6.6 TemplateRendererPort

```python
class TemplateRendererPort(Protocol):
    def render(
        self,
        template: str,
        variables: Mapping[str, object],
    ) -> str:
        ...
```

Jinja2는 Adapter의 구현 세부사항으로 둔다.

## 6.7 SchedulerPort

```python
class SchedulerPort(Protocol):
    def register(
        self,
        job: Job,
        callback: Callable[[ScheduledRun], None],
    ) -> None:
        ...

    def start(self) -> None:
        ...

    def shutdown(self) -> None:
        ...
```

Application은 APScheduler를 직접 import하지 않는다.

## 6.8 ClockPort

```python
class ClockPort(Protocol):
    def now(
        self,
        timezone: str,
    ) -> datetime:
        ...
```

테스트에서 실제 현재 시각에 의존하지 않도록 반드시 Clock Port를 사용한다.

# 7. RunJob Use Case

`RunJob`은 핵심 Application Use Case다.

생성자에서 다음 Port를 주입받는다.

```text
JobRepositoryPort
PromptLoaderPort
TemplateRendererPort
OpenWebUiPort
ExecutionRepositoryPort
ChannelResolver
ClockPort
```

개념적인 구조:

```python
class RunJob:
    def __init__(
        self,
        job_repository: JobRepositoryPort,
        prompt_loader: PromptLoaderPort,
        template_renderer: TemplateRendererPort,
        openwebui: OpenWebUiPort,
        execution_repository: ExecutionRepositoryPort,
        channel_resolver: ChannelResolver,
        clock: ClockPort,
    ) -> None:
        self.job_repository_ = job_repository
        self.prompt_loader_ = prompt_loader
        self.template_renderer_ = template_renderer
        self.openwebui_ = openwebui
        self.execution_repository_ = execution_repository
        self.channel_resolver_ = channel_resolver
        self.clock_ = clock
```

Use Case의 실행 순서:

1. Job 조회
2. 활성 여부 확인
3. 실행 ID와 scheduled time 결정
4. 중복 또는 진행 중 실행 확인
5. `try_start()`로 실행 상태 원자적 등록
6. 프롬프트 원문 로드
7. 템플릿 변수 생성
8. 프롬프트 렌더링
9. Open WebUI Port 호출
10. 응답 공백 여부 검증
11. 각 채널을 Resolver로 조회
12. 각 채널 독립 전송
13. 채널별 결과 저장
14. 최종 실행 상태 결정
15. 실행 완료 상태 저장
16. Use Case 결과 반환

한 채널이 실패해도 나머지 채널은 계속 실행한다.

최종 상태 결정:

```text
모든 채널 성공       → SUCCESS
일부 성공, 일부 실패 → PARTIAL_SUCCESS
모든 채널 실패       → FAILED
Open WebUI 호출 실패 → FAILED
중복 또는 실행 중    → SKIPPED
```

# 8. Channel Resolver와 확장성

Application은 `if channel_type == "telegram"` 같은 분기를 가져서는 안 된다.

금지 예:

```python
if destination.channel_type == "telegram":
    TelegramChannel(...)
elif destination.channel_type == "nextcloud_talk":
    NextcloudTalkChannel(...)
```

대신 `ChannelResolver` 또는 Registry를 사용한다.

```python
class ChannelResolver:
    def __init__(
        self,
        channels: Sequence[MessageChannelPort],
    ) -> None:
        self.channels_ = {
            channel.channel_type: channel
            for channel in channels
        }

    def resolve(
        self,
        channel_type: str,
    ) -> MessageChannelPort:
        try:
            return self.channels_[channel_type]
        except KeyError as exception:
            raise UnsupportedChannelError(
                channel_type
            ) from exception
```

새 채널 추가 절차는 다음만 필요해야 한다.

1. `MessageChannelPort` 구현
2. Bootstrap Container에 Adapter 등록
3. 환경변수 문서 추가
4. Contract Test 추가

기존 `RunJob` Use Case를 수정해서는 안 된다.

# 9. Fake Channel Adapter

Fake Channel은 필수 구현 대상이다.

용도:

* 단위 테스트
* 통합 테스트
* 로컬 수동 테스트
* 실제 Telegram·Nextcloud 전송 없는 Dry Run
* 응답 내용 검증
* 장애 시나리오 테스트

구현 예:

```python
@dataclass(frozen=True)
class SentMessage:
    target: str
    title: str
    body: str


class FakeMessageChannel:
    channel_type = "fake"

    def __init__(
        self,
        fail_targets: set[str] | None = None,
    ) -> None:
        self.sent_messages: list[SentMessage] = []
        self.fail_targets_ = fail_targets or set()

    def send(
        self,
        target: str,
        message: OutboundMessage,
    ) -> DeliveryReceipt:
        if target in self.fail_targets_:
            raise ChannelDeliveryError(
                f"Configured fake failure: {target}"
            )

        self.sent_messages.append(
            SentMessage(
                target=target,
                title=message.title,
                body=message.body,
            )
        )

        return DeliveryReceipt(
            external_id=f"fake-{len(self.sent_messages)}"
        )
```

Fake Channel은 운영 이미지에도 포함할 수 있지만 기본적으로 활성화하지 않는다.

활성화 환경변수 예:

```dotenv
ENABLE_FAKE_CHANNEL=false
```

운영 환경에서 `fake` 채널 Job이 발견되었는데 Fake Channel이 비활성화된 경우 해당 Job을 검증 실패 처리한다.

테스트 환경에서는 활성화한다.

```dotenv
ENABLE_FAKE_CHANNEL=true
```

## 9.1 Fake Channel Job 예시

```yaml
version: 1

id: fake-channel-test
name: Fake 채널 테스트
enabled: false

schedule:
    cron: "0 0 1 1 *"
    timezone: Asia/Seoul

    model: qwen3-80b-instruct
    skill_ids: []
    tool_ids: []
    required_tool_ids: []
    timeout_seconds: 30

    file: fake-channel-test.md

    channels:
        - type: fake
          target: test-recorder

    max_instances: 1
    skip_if_previous_running: true
    misfire_grace_seconds: 300
    retry_count: 0
    retry_delay_seconds: 1
```

# 10. Fake Open WebUI Adapter

Application 테스트에서 실제 Open WebUI를 호출하지 않는다.

Fake 구현은 다음 기능을 지원한다.

* 고정 응답 반환
* 요청 기록
* 특정 호출에서 실패
* 빈 응답 반환
* 지연 또는 timeout 예외 시뮬레이션
* Tool 호출 목록 시뮬레이션

예:

```python
class FakeOpenWebUiClient:
    def __init__(
        self,
        response_content: str = "fake response",
        exception: Exception | None = None,
    ) -> None:
        self.response_content_ = response_content
        self.exception_ = exception
        self.requests: list[OpenWebUiRequest] = []

    def generate(
        self,
        request: OpenWebUiRequest,
    ) -> OpenWebUiResponse:
        self.requests.append(request)

        if self.exception_ is not None:
            raise self.exception_

        return OpenWebUiResponse(
            content=self.response_content_,
            model=request.model,
        )
```

# 12. Bootstrap과 Dependency Injection

구체 Adapter 생성과 조립은 `bootstrap`에서만 수행한다.

```text
bootstrap/settings.py
    환경변수 로드 및 검증

bootstrap/factories.py
    Adapter 생성

bootstrap/container.py
    Port와 Adapter 조립
```

예:

```python
@dataclass
class ApplicationContainer:
    run_job: RunJob
    validate_jobs: ValidateJobs
    list_jobs: ListJobs
    scheduler: SchedulerPort
```

Production Container:

```text
OpenWebUiPort             → HttpOpenWebUiAdapter
ExecutionRepositoryPort   → SqliteExecutionRepository
JobRepositoryPort         → YamlJobRepository
PromptLoaderPort          → FilePromptLoader
TemplateRendererPort      → JinjaTemplateRenderer
SchedulerPort             → ApschedulerAdapter
ClockPort                 → SystemClock
```

모든 의존성은 생성자 주입한다.

# 13. Job 파일 구조

작업 하나당 하나의 `*.job.yaml` 파일을 사용한다.

```yaml
version: 1

id: morning-ai-news
name: 매일 아침 AI 뉴스
enabled: true

schedule:
    cron: "0 7 * * *"
    timezone: Asia/Seoul

openwebui:
    model: qwen3-80b-instruct

    skill_ids:
        - daily-news-brief

    tool_ids:
        - web-search

    required_tool_ids: []

    timeout_seconds: 600

prompt:
    file: morning-ai-news.md

    variables:
        language: ko
        max_items: 5

delivery:
    send_on_success: true
    send_on_failure: true

    channels:
        - type: nextcloud_talk
          target: personal

        - type: telegram
          target: personal

execution:
    max_instances: 1
    skip_if_previous_running: true
    misfire_grace_seconds: 300
    retry_count: 2
    retry_delay_seconds: 30
```

YAML Adapter는 이 구조를 외부 DTO로 읽고 Domain Model로 변환한다.

Pydantic Model을 Domain Model로 그대로 사용하지 않는다.

변환 흐름:

```text
YAML
 ↓
JobConfigDto
 ↓
Mapper
 ↓
Domain Job
```

검증 규칙:

* `version`은 현재 `1`만 허용
* Job ID는 전체 파일에서 유일
* Cron은 표준 5필드
* 타임존은 유효한 IANA 이름
* 프롬프트는 `file` 또는 `text` 중 하나만 지정
* 프롬프트 파일은 지정된 디렉터리 내부로 제한
* 하나 이상의 채널 필요
* 등록되지 않은 채널 타입 거부
* `enabled: false`는 로드하지만 스케줄 미등록
* 한 파일 오류가 전체 서비스 시작을 막지 않음
* CLI `validate`에서는 오류 파일이 하나라도 있으면 종료 코드 1

# 17. Retry 책임

Retry 정책은 재사용 가능한 Application Service 또는 Decorator Adapter로 구현한다.

권장 방식:

```text
OpenWebUiPort
   ↑
RetryingOpenWebUiAdapter
   ↑
HttpOpenWebUiAdapter
```

채널도 동일한 Decorator 구조를 사용할 수 있다.

```text
MessageChannelPort
   ↑
RetryingMessageChannel
   ↑
TelegramMessageChannel
```

또는 Use Case에서 공통 Retry Service를 사용할 수 있다.

어느 방식을 선택하든 다음 조건을 만족해야 한다.

* Retry 로직을 Telegram과 Nextcloud에 복사하지 않음
* HTTP 429, 5xx, timeout, 연결 오류만 재시도
* 400, 401, 403은 기본적으로 재시도하지 않음
* Fake Adapter로 Retry 테스트 가능
* 지수 백오프 지원
* 테스트에서는 실제 sleep하지 않도록 Sleeper Port 또는 주입 가능한 wait 함수 사용

테스트에 실제 `time.sleep()`을 사용하면 안 된다.

필요하면 다음 Port를 둔다.

```python
class SleeperPort(Protocol):
    def sleep(self, seconds: float) -> None:
        ...
```

Production은 실제 sleep, Test는 기록만 하는 Fake Sleeper를 사용한다.

# 18. Scheduler Adapter

APScheduler는 Inbound Adapter다.

Scheduler Adapter는 예약 시점에 Application Use Case를 호출한다.

```text
APScheduler callback
        ↓
RunJobCommand 생성
        ↓
RunJob.execute(command)
```

Scheduler Callback에 비즈니스 로직을 넣지 않는다.

금지:

```python
def cron_callback():
    prompt = open(...)
    response = requests.post(...)
    send_telegram(...)
```

허용:

```python
def cron_callback():
    run_job.execute(
        RunJobCommand(
            job_id=job_id,
            scheduled_time=scheduled_time,
        )
    )
```

```makefile
fake-run:
	docker compose exec \
		-e ENABLE_FAKE_CHANNEL=true \
		prompt-dispatcher \
		python -m prompt_dispatcher run $(JOB) --fake-channel
```

`make up`은 이미지를 자동 빌드하지 않는다.

# 30. 완료 조건

다음 조건을 모두 만족해야 한다.

## Architecture

* Domain이 Framework와 Adapter에 의존하지 않음
* Application이 구체 Adapter에 의존하지 않음
* Port가 Application 계층에 정의됨
* Adapter가 Port를 구현함
* Bootstrap에서 의존성 조립
* RunJob Use Case에 외부 API 직접 호출 코드 없음
* 새 채널 추가 시 RunJob 수정 불필요
* Fake Channel로 실행 가능
* Fake Open WebUI Client로 테스트 가능
* In-memory Repository로 테스트 가능
* Fake Clock으로 시간 고정 가능

## Functional

* Job YAML 로드
* Cron 등록
* 프롬프트 렌더링
* Open WebUI API 호출
* Skill ID 전달
* Tool ID 전달
* Telegram 전송
* Nextcloud Talk 전송
* 채널별 실패 독립 처리
* 실행 상태 SQLite 저장
* 중복 실행 방지
* 오래된 RUNNING 실행 복구
* CLI 수동 실행
* Dry Run
* Fake Channel Run
* Health API

## Docker

* `docker build -t prompt-dispatcher:local .` 성공
* Compose에 `build:` 없음
* Compose에서 `prompt-dispatcher:local` 사용
* 비-root 실행
* Health Check 성공

## Test

* Domain Unit Test 통과
* Application Unit Test 통과
* Fake Adapter 기반 End-to-End Test 통과
* Adapter Integration Test 통과
* Channel Contract Test 통과
* SQLite 중복 실행 테스트 통과
* 한 채널 실패 후 다음 채널 실행 테스트 통과
* 실제 외부 서비스 없이 전체 테스트 가능
* 테스트에서 실제 sleep 미사용
